# P0.2 — Inventario de datos y destinatarios

Fecha: 2026-09-07. Commit: `7f8f9cb987779b6e4df417b3195040a7b4b7dc60`. Complementa el [informe](INFORME.md) y la [propuesta de ciclo de vida](CICLO_DE_VIDA.md).

Clasificación operativa propuesta: **C1 público**; **C2 interno**; **C3 personal/confidencial**; **C4 restringido** (secretos, imágenes identificables y perfiles de alto impacto). Es una clasificación de seguridad, no una declaración automática de categoría jurídica. Una imagen facial no implica por sí sola que exista identificación biométrica; aquí se extraen características del rostro para estimar atención, sin comparación de identidad encontrada. Hasta revisar su uso y base jurídica, se propone C4 para imágenes y características faciales.

**E**: código/configuración; **I**: posibilidad inferida; **Q**: dato de operación sin confirmar. “Almacenado” describe rutas implementadas, no registros observados en una BD. La ingesta ML tiene fallos conocidos de P0.1; no elimina las otras rutas de persistencia ni el procesamiento previo a un fallo.

Población del estudio: estudiantes universitarios de 18 años o más en Ecuador; menores excluidos por instrucción corregida del usuario. La elegibilidad deberá comprobarse antes de recoger datos. El inventario técnico describe capacidades del código, no acredita que este filtro ya exista.

## Acceso interno: actual frente a objetivo propuesto

| Actor | Acceso observado o posible | Límite propuesto, pendiente de aprobación |
|---|---|---|
| Anónimo | Login/OAuth/alta pública; ML handlers no autentican a nivel app; altas admin reproducidas en P0.1 | Alta sin rol privilegiado; cero lectura de expedientes; ingesta ML solo autenticada por servicio y sesión |
| Estudiante | Sus eventos/D2R/matrículas por queryset; `/users/` global y fallos de edición/rol de P0.1 rompen el aislamiento esperado | Solo datos propios; sin escoger identidad/propietario ajeno ni reescribir resultados calculados arbitrariamente |
| Docente | Datos de alumnos relacionados mediante matrículas/curso; D2R y notificaciones pueden abarcar información fuera del curso concreto; filtros no incluyen consentimiento de compartir | Necesidad pedagógica documentada, curso y vigencia de matrícula, detalle mínimo; sin frames ni datos de otros docentes por defecto |
| Admin de aplicación | Usuarios/cursos/analytics/políticas/reportes según código; rol basta para acceso privilegiado | Funciones separadas de soporte, académico, datos e investigador; acceso excepcional trazado |
| Servicio ML | Procesa imágenes en claro en RAM; cuenta de servicio por defecto admin/staff/superuser; POST actual omite token | Identidad exclusiva de ingesta; sin CRUD de cuentas/cursos ni exportación; autenticación ligada a sesión |
| Operador/DBA/CI | Shell, DB, variables, imágenes, logs y datasets según credenciales que tenga; IAM real no revisado | Cuentas nominativas, mínimo privilegio, MFA para consola, acceso temporal aprobado, auditoría y separación de custodio de claves |
| Investigador | Solo solicitud administrativa en app; export real por CLI con privilegios DB | Dataset aprobado, seudónimos por proyecto, mapa separado, contrato de uso y prohibición de reidentificar; registro de receptor/versiones/expiración |
| Proveedor | Datos descritos en flujos; contrato/tenant/región/subencargados no revisados | Registro de finalidad, ubicación, retención, soporte, devolución/borrado, incidentes y transferencias; verificar antes de datos reales |

No confundir “agregado” con anónimo: un curso pequeño o un snapshot individual permite atribuir resultados. La posibilidad de borrar un registro por un admin tampoco equivale a un proceso completo de ejercicio de derechos.
